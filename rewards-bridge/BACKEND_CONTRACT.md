# Что реализовать бэкендерам для карточек Roblox

Назначение: из пака в Roblox выпадает карточка с номиналом. Сервер Roblox запрашивает
код у вашего API и показывает ответ игроку. Код погашается во внешнем приложении
(бот, сайт, Mini App — не важно). Номинал начисляется во внешний баланс, не в Roblox.

## Принцип работы: что за чем происходит

Короткая цепочка: **пак в Roblox → выпадение карточки → запрос серверу бэкенда →
создание и сохранение кода → показ кода в Roblox → ввод во внешнем приложении →
однократное начисление на внешний баланс**.

1. **Игрок открывает пак в Roblox.** Сервер игры определяет результат выпадения.
   Если выпала кодовая карточка, например на 1000 пиратов, он выбирает её тип
   `pirate_card_1000`. Клиент игрока не назначает награду и не генерирует код.
2. **Roblox сохраняет факт выпадения.** Сервер создаёт постоянный `dropId` этого
   выпадения и сохраняет его, владельца, тип карточки и ожидание доставки вместе
   с расходом пака. Это нужно, чтобы при сбое или перезаходе не потерять награду
   и не выдать её второй раз.
3. **Сервер Roblox обращается к вашему API.** Через HTTPS он отправляет
   `POST /api/roblox/rewards/issue`: `universeId`, `dropId`, `robloxUserId`, `rewardId`.
   В заголовке передаётся серверный ключ. Инициатор запроса — Roblox;
   открывать входящий HTTP-сервер внутри плейса не нужно.
4. **Бэкенд создаёт настоящий активируемый код.** Проверяет ключ и разрешённую
   игру, определяет сумму по своему каталогу `rewardId`, генерирует случайный код
   и сохраняет в БД код, сумму, владельца выпадения и статус «не активирован».
   Только после сохранения возвращает код и сумму Roblox. Если такой `dropId`
   уже обработан, возвращает прежний код вместо создания нового.
5. **Roblox показывает карточку игроку.** На ней отображаются именно код и сумма
   из ответа бэкенда. На этом этапе внешний баланс ещё не пополняется.
   Пока API недоступен, карточка остаётся в ожидании; Roblox повторяет запрос
   с тем же `dropId`. После перезахода уже выданные коды доступны через историю API.
6. **Игрок открывает внешнее приложение.** Это может быть ваш бот, сайт или
   Mini App. Он входит в свой аккаунт и вводит код с карточки Roblox.
   Интерфейс отправляет код бэкенду; получателя награды сервер определяет
   по авторизованному аккаунту, а сумму — по записи кода в БД.
7. **Бэкенд активирует код и начисляет награду.** В одной транзакции проверяет,
   что код действителен и не использован, увеличивает внешний баланс на его
   номинал, записывает операцию в журнал и помечает код активированным.
   Если операция не завершилась, частичного начисления или списанного без
   награды кода быть не должно.
8. **Игрок видит обновлённый внешний баланс.** Повторная отправка того же кода
   не начисляет награду ещё раз. В истории карточек Roblox бэкенд возвращает
   статус `redeemed`; игра узнаёт его при следующем чтении истории API.

**Пример:** игрок выбил карточку «1000 пиратов». Roblox получил от бэкенда код
и показал его. До активации баланс на сайте — 200. Игрок ввёл код на сайте:
баланс стал 1200, код помечен использованным. При повторном вводе баланс
остаётся 1200. Игровая валюта Roblox при этом не начисляется и не списывается.

**Кто за что отвечает:** Roblox — за честное выпадение, сохранение результата
пака и показ карточки; бэкенд — за генерацию, хранение и однократное погашение
кодов, журнал и внешний баланс; бот/сайт/Mini App — за вход пользователя,
ввод кода и отображение результата. Генерация кодов не выполняется в браузере
Mini App или на клиенте Roblox.

В текущем варианте код можно передать: его активирует первый пользователь,
который его знает. Если активировать должен только владелец Roblox-карточки,
потребуется привязка Roblox-аккаунта к аккаунту внешнего приложения.

## Что уже сделано со стороны Roblox

`roblox/RewardCodes.lua` — серверный модуль приёма: очередь ожидающих запросов,
повтор при сетевых ошибках, проверка ответа, восстановление карточек из истории API.
`roblox/RewardCodesBootstrap.server.lua` — подключение с секретом Creator Hub,
уведомление конкретного игрока и чтение его истории через RemoteFunction.
Никогда не выдавать API-ключ клиенту Roblox.

API вызывается сервером игры через HttpService. Входящий HTTP-порт в Roblox не нужен.
Open Cloud не требуется. Ваш API должен быть доступен игровым серверам по HTTPS.

## Обязательные методы

### 1. Выдать код: POST /api/roblox/rewards/issue

Заголовки: `Content-Type: application/json`, `X-API-Key: <серверный секрет>`.

```json
{
  "universeId": 123,
  "dropId": "persisted-pack-drop-guid",
  "robloxUserId": 456,
  "rewardId": "pirate_card_1000"
}
```

`dropId` создаётся один раз при серверном определении результата пака, сохраняется
вместе с расходом пака и не меняется при повторе/перезаходе. Это ключ идемпотентности,
а не случайный ID каждого сетевого запроса. Авторизованный universeId определяется
по серверному ключу, а не только по полю JSON.

Успех HTTP 200:

```json
{
  "dropId": "persisted-pack-drop-guid",
  "robloxUserId": 456,
  "rewardId": "pirate_card_1000",
  "amount": 1000,
  "code": "0123-4567-89AB-CDEF-0123-4567-89AB-CDEF",
  "status": "issued",
  "createdAt": 1793613744343
}
```

- `amount`: положительное целое, берётся из вашего каталога rewardId. Не доверять сумме клиента.
- `code`: случайный криптографически стойкий код; в прототипе 128 бит, 32 hex-символа,
  разбитые дефисами на группы по 4. Генерирует только ваш сервер.
- Повтор `(universeId, dropId)` возвращает **тот же код и номинал**, даже после погашения.
  В последнем случае `status` будет `redeemed`.
- Если тот же dropId пришёл с другим владельцем/rewardId — 409 `drop_conflict`, без новой выдачи.
- Ответ только после commit в БД. Потерянный ответ не должен порождать второй код.

### 2. История: GET /api/roblox/rewards?userId=456&after=0

Тот же `X-API-Key`. Ответ `{"cards":[...],"nextCursor":null}`.
Каждая карточка имеет формат выше. Возвращать только карточки указанного игрока
в universe, разрешённом ключу. По 50 записей, стабильный порядок по внутреннему ID.
Если есть продолжение — `nextCursor` положительное целое; иначе null.
Roblox берёт userId у вошедшего Player, клиент не выбирает чужого владельца.

### 3. Погашение во внешнем приложении

Прототип использует `POST /api/redeem` с `{"code":"..."}` и отдаёт
`{"amount":1000,"balance":1000,"alreadyRedeemed":false}`.
Способ авторизации внешнего пользователя ваша команда выбирает под своё приложение.
Telegram здесь необязателен. Публичный интерфейс не должен сам назначать userId или сумму.

Одна транзакция БД должна:
1. Найти и заблокировать код.
2. Проверить, что он не погашен.
3. Записать зачисление в журнал с уникальным reward ID и изменить баланс.
4. Пометить код погашенным этим пользователем.

Повтор того же пользователя — успешный ответ с `alreadyRedeemed:true`, без начисления.
Другому пользователю — 409 `code_used`. В этом варианте код предъявительский:
погасит первый, кто его знает. Для ограничения владельцем нужна отдельная привязка аккаунтов.

## Ошибки и эксплуатация

JSON `{"error":"machine_readable_code"}`:
400 — неправильные поля/rewardId; 401 — неверный ключ; 403 — чужой universe;
409 — конфликт/погашенный код; 429 — лимит (`Retry-After`); 503 — временный сбой.
Не подменять ошибку ответом 200 с пустым кодом. Не выдавать новый код после таймаута.

БД любая, если сохраняются атомарность и уникальности:
`UNIQUE(universe_id,drop_id)`, уникальный код, `UNIQUE(ledger.reward_id)`.
Если баланс в отдельном сервисе, нужен идемпотентный метод зачисления по reward ID,
а не два несогласованных запроса. Нужны backup, мониторинг ошибок и лимиты выдачи.

В репозитории есть эталонный сервер Node.js + SQLite, который можно заменить,
сохранив этот контракт. `npm run demo` запускает стенд без Telegram на localhost.
Тестовый ключ хранится в `data/demo/studio.key`, не входит в git и не отдаётся браузеру.

## Подключение нашей стороне

Передать разработчику Roblox: HTTPS base URL, ключ для нужного universe (безопасным
каналом), список rewardId и номиналов, лимиты API, контакты для разбора ошибок.
Roblox сохраняет ключ как Creator Hub Secret `PIRATE_REWARDS_API_KEY`.

В обработчике реального пака нужно одной записью сохранить его расход, результат,
dropId и `deliveryPending`. Затем вызывать `Codes.Queue`; на false повторять позже.
Без этого шага нельзя считать реальную выдачу пака подключённой. В текущем репозитории
обработчик именно кодовых карточек не найден, поэтому проверка проводится в отдельном плейсе.

## Границы локальной проверки

Тестовый плейс `data/RewardCodesStudio.rbxl` делает реальные HTTP-запросы из игрового
сервера Roblox Studio к API, который использует настоящую SQLite. Генерация в Roblox отсутствует.
Кнопки выдачи/погашения есть только в Studio-стенде, не в production-bootstrap.

В неопубликованном плейсе очередь ожидающих запросов хранится в памяти Studio,
потому что DataStore требует опубликованную игру. Боевой модуль использует DataStore;
его сохранность при аварии сервера нужно отдельно проверить в опубликованном тестовом universe.
Публичный HTTPS и секрет Creator Hub также требуют отдельного smoke-теста после развёртывания.
