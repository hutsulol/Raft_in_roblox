# Карточки «Пират»: Roblox → код → Telegram

Запускаемый прототип для передачи команде бота: API, Mini App, SQLite, необязательный
Telegram-бот и серверный адаптер Roblox. Node.js 24+. Для запуска API нет npm-зависимостей.
Генерация и номинал кода принадлежат серверу бота. Баланс бота отдельный от игровой валюты.

## Запуск проверки именно в Roblox (без Telegram)

```powershell
npm run studio:build
npm run demo
```

Открыть `data/RewardCodesStudio.rbxl` в Roblox Studio и нажать Play. На экране:
«Открыть тестовый пак» → «Проверить активацию и защиту от повтора».
Код генерирует Node-сервер, Roblox получает его настоящим HttpService-запросом.
Сайт http://127.0.0.1:8787 показывает тот же баланс и позволяет погасить полученный код.
Чтобы проверить историю, остановить/заново запустить Play и нажать «Восстановить карточку».

Для стенда сборщик создаёт локальный серверный ключ (gitignored), HTTP уже включён
в отдельном тестовом плейсе. В опубликованной игре Studio-режим запрещён проверкой IsStudio.
Локальная очередь стенда в памяти; production-модуль использует DataStore.
Не публиковать сам CodeLab: его кнопки специально дают тестовые награды.

Команде бэкенда передать [BACKEND_CONTRACT.md](BACKEND_CONTRACT.md).
Итоги реального прогона Studio — [STUDIO_TEST_RESULTS.md](STUDIO_TEST_RESULTS.md).

## Быстрый запуск без Telegram и хостинга

Из этой папки:

```powershell
npm run demo
```

Открыть http://127.0.0.1:8787. Нажать «Получить тестовую карточку», затем «Активировать код».
Это настоящий HTTP-запрос, случайный код и транзакция SQLite, а не имитация баланса в браузере.
Повторная активация не увеличит баланс. Обновление страницы и перезапуск сервера его сохраняют.
Кнопка карточки имитирует авторитетный запрос Roblox: реального пака в локальной демонстрации нет.
Демонстрационная база и ключ лежат в `data/demo/`, отдельно от боевых данных.
Демо — один локальный тестовый пользователь. Не выставлять его через публичный reverse proxy/tunnel.

## Подключение Telegram и HTTPS

1. Создать отдельного тестового бота через BotFather; скопировать `.env.example` в `.env`.
2. Заполнить `BOT_TOKEN`, `ROBLOX_UNIVERSE_ID` (Universe ID, не Place ID), `PUBLIC_URL`.
3. Сгенерировать **два разных** секрета командой ниже: один для `ROBLOX_API_KEY`, второй
   для `CODE_ENCRYPTION_KEY`. Не присылать токен бота и секреты в чат, не коммитить `.env`.
4. Запустить `npm start`. API слушает `127.0.0.1:8787`. Перед ним нужен HTTPS reverse proxy
   с доменом и сертификатом, например конфигурация `Caddyfile.example`.
5. В другом терминале запустить `npm run bot`. Отправить боту `/start`: появится кнопка Mini App.
   Также доступны `/balance`, `/redeem КОД` и отправка кода простым сообщением.
   Только один polling-worker на токен; он откажется работать при существующем webhook,
   не удаляя настройки чужого бота. Команда может перенести обработчики в свой webhook-бот.
6. Проверить открытие Mini App в Telegram. В production вход возможен только с проверенной
   подписью `Telegram.WebApp.initData`; переданный клиентом `userId` не используется.

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Номиналы примера: 100, 500, 1000. Меняются в `store.mjs` → `REWARDS`; разрешённые rewardId
также указываются в Roblox bootstrap. Существующие коды сохраняют первоначальный номинал.
В реальной Mini App нет кнопки бесплатной генерации и нет доступа к серверному ключу.

## Подключение к Roblox

В текущем океане не найден обработчик пака, выдающего кодовую карточку. Поэтому адаптер
вынесен в `roblox/`, не включён в основной плейс и не меняет шанс выпадения/игровой баланс.
Это готовая точка интеграции, а не утверждение, что существующие паки уже подключены.

1. Поместить `RewardCodes.lua` как ModuleScript `RewardCodes` в ServerScriptService,
   рядом `RewardCodesBootstrap.server.lua`. В отдельном `roblox/default.project.json`
   оба файла перечислены явно для Rojo.
2. Указать HTTPS URL API в `API_URL`. В Creator Hub создать секрет
   `PIRATE_REWARDS_API_KEY`, равный `ROBLOX_API_KEY`, и ограничить его доменом API.
   Включить Allow HTTP Requests. Для теста DataStore в Studio нужны соответствующие
   разрешения; здесь Studio автоматически не запускается.
3. В авторитетном серверном обработчике открытия пака **одной записью его сейва**
   сохранить расход пака, результат и постоянный `dropId` (GUID генерируется один раз).
   Сохранить там же признак `deliveryPending=true`. Только после успешной записи вызвать:

```lua
local Codes = require(game.ServerScriptService.RewardCodes)
local accepted, why = Codes.Queue(player, savedPackResult.dropId, savedPackResult.rewardId)
-- accepted=true: награда надёжно записана в outbox, но код ещё может быть не готов.
-- accepted=false: оставить deliveryPending и повторить с ТЕМ ЖЕ dropId.
-- После accepted=true можно снять deliveryPending в сейве пака.
```

4. При загрузке сейва повторять Queue для всех `deliveryPending`. Это закрывает разрыв
   между записью расхода пака и записью outbox. Простого вызова Queue после удаления пака
   без сохранённого результата недостаточно: при аварии награда может потеряться.
5. После подтверждения API адаптер удалит запись outbox. Сбой удаления безопасен:
   повтор вернёт тот же код. Ожидающие записи повторяются каждые 30–40 секунд, пока игрок
   онлайн, и при следующем входе. Офлайн-доставка без следующего входа здесь не реализована.
6. UI карточек слушает `RewardCodeIssued` (сервер → конкретный игрок) и при открытии
   читает `RewardCodesList:InvokeServer(cursor)`. Ответ `{cards, nextCursor}`; по 50 записей.
   Отображать именно `code`, `amount`, `status` из ответа. При ошибке показывать «ожидается
   выдача», не придумывать временный код. История из API восстанавливает пропущенные уведомления.

Не подключать Queue к RemoteEvent, которому клиент передаёт сумму, rewardId или dropId.
В текущем `RewardSystem.server.lua` выбор оружия приходит от клиента: его нельзя без
отдельной проверки использовать как основание для выпуска наград бота.

## HTTP-контракт для другой команды

Все запросы и ответы JSON. Production обслуживается только через HTTPS.

| Метод и путь | Доступ | Назначение |
|---|---|---|
| `POST /api/roblox/rewards/issue` | `X-API-Key` | Создать/вернуть код по сохранённому выпадению |
| `GET /api/roblox/rewards?userId=42&after=0` | `X-API-Key` | Карточки игрока, 50 на страницу |
| `GET /api/me` | `X-Telegram-Init-Data` | Баланс и последние 20 начислений |
| `POST /api/redeem` | `X-Telegram-Init-Data` | Погасить код и начислить баланс |
| `GET /health` | Публичный | Проверка доступности процесса и SQLite |

Выдача:

```json
{"universeId":123,"dropId":"persisted-pack-drop-guid","robloxUserId":42,"rewardId":"pirate_card_1000"}
```

Ответ:

```json
{"dropId":"persisted-pack-drop-guid","robloxUserId":42,"rewardId":"pirate_card_1000","amount":1000,"code":"XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX","status":"issued","createdAt":1793606400000}
```

`POST /api/redeem`: `{"code":"..."}` →
`{"amount":1000,"balance":1000,"alreadyRedeemed":false}`.
Повтор того же пользователя возвращает `alreadyRedeemed:true` без нового начисления.
Другому пользователю — `409 code_used`. Неизвестный код — `404 code_not_found`.
Изменение владельца/номинала при том же dropId — `409 drop_conflict`.
Сбой БД — `503 temporarily_unavailable`; лимит — `429` и `Retry-After: 60`.
На таймаут, 429, 503 повторять исходную операцию с прежним идентификатором.
На 401/403/409 нужно исправить конфигурацию/конфликт, а не создавать новый dropId.

Код — предъявительский: его погашает первый знающий код пользователь. Roblox ID записан
для истории выдачи, но привязка Roblox ↔ Telegram не реализована. Если награда должна
принадлежать строго владельцу карточки, перед публичным запуском нужна привязка аккаунтов.

## Надёжность и база

- Код: 128 случайных битов, генерируется криптографическим RNG на сервере бота.
- В БД SHA-256 для поиска и AES-256-GCM для восстановления кода при повторной выдаче.
- `UNIQUE(issuer, drop_id)` не допускает повторного выпуска на то же выпадение.
- `BEGIN IMMEDIATE` объединяет погашение, изменение баланса и запись журнала.
  `UNIQUE(ledger.reward_id)` дополнительно запрещает повторное начисление.
- SQLite WAL + synchronous FULL, ожидание блокировки 5 секунд. Код/баланс нельзя
  менять напрямую через Mini App. Лимит погашений общий для бота и Mini App.
- Проверка Telegram HMAC, срок входа 1 час; секреты и тела запросов не пишутся в логи.
- Смена ключа шифрования без миграции останавливает запуск: не теряйте ключ.
- Outbox Roblox остаётся при ошибках. Если БД Roblox недоступна, Queue возвращает false,
  обработчик пака обязан сохранить и повторить pending-результат.

SQLite рассчитана на один хост с локальным диском; **боевую БД не хранить на OneDrive,
сетевой папке или эфемерном диске контейнера**. Для хостинга укажите DB_PATH на постоянном
локальном диске вне этого рабочего репозитория. API и polling-бот используют одну БД.
Нужны резервные копии через SQLite backup API/штатный инструмент вместе с ключом шифрования;
простое копирование открытого .sqlite без WAL не является корректным backup.

Другая команда может заменить `Store` на PostgreSQL или свою БД, сохранив контракт,
уникальные ограничения, журнал и атомарность. Если баланс уже живёт в другой БД/сервисе,
нельзя заменить транзакцию на два независимых запроса: нужен идемпотентный метод зачисления
с reward ID и согласованный outbox. Секрет Roblox даёт право выпуска: доступ к нему только
у сервера. Для публичной нагрузки добавить мониторинг ошибок/outbox, резервное копирование,
периметровый rate limit и алерты на аномальный объём выдачи.

## Проверки

```powershell
npm ci
npm test
node test/check-lua.mjs
npx playwright install chromium
npx playwright test
rojo build roblox/default.project.json -o data/adapter.rbxl
```

Тесты проверяют сохранение после перезапуска, повтор выдачи, запрет подмены номинала,
четырёх конкурентных погасителей на отдельных SQLite-соединениях, откат при ошибке журнала,
Telegram-подпись/срок, HTTP-авторизацию и ограничения, полный HTTP-цикл и мобильный интерфейс.
Браузерный тест работает headless, без управления окнами пользователя.

Проверка опубликованного Roblox → публичный HTTPS → настоящий Telegram требует домена,
бот-токена, секрета Creator Hub и настроенного тестового плейса. Локальные тесты этого
не заменяют. Перед запуском проверить: выпадение → перезаход → активация → повтор активации,
а затем повторить при временно выключенном API и после перезапуска API.

Основание выбора способа (проверено по документации):
[Roblox HttpService](https://create.roblox.com/docs/cloud-services/http-service),
[Roblox Secrets](https://create.roblox.com/docs/reference/engine/classes/HttpService#GetSecret),
[Telegram initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).
Roblox Open Cloud для этой схемы не нужен: инициатор выдачи — сервер игры.
